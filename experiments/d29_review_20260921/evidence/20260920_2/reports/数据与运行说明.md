## 七、冻结记录的绑定（**只读绑定，绝不重写**）

本轮与上一轮的关键差别：**本轮有真正的生产者** `work/_freeze_prereg.py`，
它有两道守卫——拒绝覆盖已存在的记录（`FREEZE_RECORD_ALREADY_EXISTS`）、
拒绝在 `reports/phase1_arms.json` 存在后写入（`FORWARDS_HAVE_ALREADY_RUN`）。
⇒ 记录**可以被重新推导并比对，但不可能被重新打上新的时间戳**。

`_verify_prereg_freeze.py` **在本轮前向之后重跑**（`reports/prereg_freeze_check.json`）：

```

FAILED : mtime(arms.json) < mtime(freeze)
FAILED : recorded_at_utc postdates every input it binds
FAILED : recorded_at_utc lies in the same window as the mtimes
frozen before the first forward by 31.3 min (from mtimes, not from the record)
checker exclusion: CHECKER_EXCLUSION_REPOINTED (FROZEN_SHA=da00a38eb2aef43d…)
freeze record sha256 5493806e9a41c13f… -- UNCHANGED by this run: it binds, it never writes
```

**两条 PENDING 已解除**：`n_forwards == forward_count` 与
`mtime(freeze) < mtime(phase1_arms.json)` 现在都有产物可查，且**都指向"冻结先于首次前向"**。

**三条 FAILED 的实质（不夸大、不掩盖）**：见偏离 **E1**。核心是
`phase0_gates.py` 在 A6 修复之后**被重跑**（不重跑就是拿旧证据冒充新核），
于是它的产物 `arms.json` 被**重写了一次**，`mtime` 落到冻结记录之后。
**内容证据**：`arms.json` 的 sha 前后**逐字节相同**
（`58a96753d80c071ae395388e3e52afcea9bbd934db1ea2ea4b1b83d0833cf5`），
其 `table_sha256` 与冻结记录**逐位相同**。
**仍然成立的、更强的替代证明**：预注册 md 的
`mtime = 2026-09-20T06:01:57.975682+00:00` **早于**冻结记录的
`2026-09-20T06:03:21.911768+00:00`，其 sha256
`da00a38eb2aef43dff8859d8d30e3a0b308a8b15b33234ec31aa86e5d3956437` 与 `53237` 字节
**等于**冻结记录里的对应字段，**且该 md 在其 §五 处已经载明臂表哈希**
⇒ 一份被冻结记录按内容地址绑定、mtime 早于冻结记录的文件，
**在冻结之前就已经载明了臂表哈希**。

**处置**：**不改**冻结记录、**不回拨** `arms.json` 的 mtime、**不删**这三条 FAILED。
只做一件事：给 `phase0_gates.py` 的两个写盘点加**幂等写**（内容相同则不写，mtime 不动）。
该改动**不能**修好本轮的次序，**也不是**在让检查通过——重跑验证器后三条 FAILED **依旧 FAILED**；
它只对**下一次重跑**有效。已实测幂等：重跑报
`phase0_gates.json UNCHANGED (not rewritten)`、`arms.json UNCHANGED (not rewritten)`。
